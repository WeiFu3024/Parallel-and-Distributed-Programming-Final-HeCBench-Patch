## 1. Prompt Templates

### 1.1 System Prompt (shared across all cells)

```
You are a GPU performance engineer.
Your task is to optimize the provided CUDA kernel for maximum performance.
Output only the complete, compilable CUDA source code as a single .cu file.
Do not include explanatory text outside of code comments.

<Constraints>
  - Do NOT search the internet or reference external documentation.
  - Do NOT use acceleration libraries (cuBLAS, cuFFT, cuDNN, Thrust).
  - Do NOT modify host-side validation logic or input data generation.
  - Do NOT change data types or problem sizes from the original code.
  - You do NOT have access to a compiler, profiler, or runtime environment.
  - All compilation and profiling is handled externally.
</Constraints>
```

### 1.2 Cell A — Round 1 (code only)

```
Optimize the following CUDA kernel for maximum GPU performance.

{{Source Code Path}}
```

### 1.3 Cell B — Round 1 (code + context)

```
Use the following hardware and algorithmic context to guide your optimization:

{{CONTEXT_XML}}

Optimize the following CUDA kernel for maximum GPU performance.

{{Source Code Path}}
```

### 1.4 Cell C — Round 1

Identical to Cell B (Section 1.3). Same system prompt, same user prompt.

### 1.5 Cell C — Round 2+ (Nsight feedback)

```
Your previous kernel has been profiled. Below are the full Nsight Compute
results for both the baseline kernel and your kernel:

{{FEEDBACK_XML}}

Based on this profiling data, produce an improved version of the kernel.
Output only the complete, compilable CUDA source code.
```

### 1.6 Correctness Retry (all cells, all rounds)

Used when the LLM's submission fails to compile or fails numerical validation.
The raw error output is passed through without human interpretation.

```
Your submission failed with the following error:

<Error>
{{ERROR_OUTPUT}}
</Error>

Fix the issue and resubmit the complete CUDA source code.
```

### 1.7 Placeholder Reference

| Placeholder | Content |
|-------------|---------|
| `{{BASELINE_CODE}}` | The HeCBench benchmark's original `.cu` file path |
| `{{CONTEXT_XML}}` | `<Context_Normalization>` XML generated by the analysis LLM |
| `{{FEEDBACK_XML}}` | `<Iteration_Feedback>` XML generated by `profile_to_xml.py` |
| `{{ERROR_OUTPUT}}` | Raw `stderr` from `nvcc` (compile error) or validation diff output |

## 2. Directory Structure

The experiment runs in two parallel variants with identical internal structure:

```
experiment-cuda/   ← CUDA variant (.cu / nvcc)
experiment-omp/    ← OpenMP target variant (.cpp / nvc++ -mp=gpu)
```

Each variant follows the same layout (shown for CUDA; OMP uses `.cpp` instead of `.cu`):

```
experiment-{cuda|omp}/
│
├── config/
│   ├── hardware_spec.txt              # output of hardware_spec.sh
│   └── system_prompt.txt              # shared system prompt (Section 1.1)
│
├── scripts/
│   ├── compile.sh                     # compile LLM attempt → compile.log + binary
│   ├── validate.sh                    # run + correctness check → validate.log
│   ├── init_experiment.sh             # creates directory tree, copies baseline
│   ├── profile_to_xml.py             # ncu CSV → Iteration_Feedback XML
│   └── hardware_spec.sh              # hardware info collector
│
└── results/
    └── {benchmark_name}/
        │
        ├── baseline/
        │   ├── main.cu  (or .cpp)     # original HeCBench source (copy)
        │   ├── nsight_raw.csv         # ncu --csv output
        │   └── nsight.xml             # parsed profile in standard XML format
        │
        ├── cell_a/
        │   └── round_1/
        │       ├── attempt_1/
        │       │   ├── main.cu        # LLM output
        │       │   ├── compile.log    # compiler stdout+stderr
        │       │   └── validate.log   # runtime output + correctness check
        │       ├── attempt_2/         # if correctness retry
        │       ├── attempt_3/         # if correctness retry
        │       ├── final.cu           # copy of the passing attempt's source
        │       ├── nsight_raw.csv     # ncu output of final
        │       └── nsight.xml         # parsed profile
        │
        ├── cell_b/
        │   ├── context.xml            # Context_Normalization from analysis LLM
        │   └── round_1/
        │       ├── attempt_1/
        │       │   ├── main.cu
        │       │   ├── compile.log
        │       │   └── validate.log
        │       ├── ...
        │       ├── final.cu
        │       ├── nsight_raw.csv
        │       └── nsight.xml
        │
        └── cell_c/
            ├── context.xml            # same context as cell_b
            ├── round_1/
            │   ├── attempt_1/
            │   │   ├── main.cu
            │   │   ├── compile.log
            │   │   └── validate.log
            │   ├── ...
            │   ├── final.cu
            │   ├── nsight_raw.csv
            │   └── nsight.xml
            │
            ├── round_2/
            │   ├── feedback.xml       # Iteration_Feedback sent to LLM
            │   ├── attempt_1/
            │   │   ├── main.cu
            │   │   ├── compile.log
            │   │   └── validate.log
            │   ├── ...
            │   ├── final.cu
            │   ├── nsight_raw.csv
            │   └── nsight.xml
            │
            └── round_3/
                ├── feedback.xml
                ├── attempt_1/
                │   └── ...
                ├── final.cu
                ├── nsight_raw.csv
                └── nsight.xml
```

### Key Conventions

- `attempt_N/main.{cu|cpp}` — the Nth submission from the LLM in that round (correctness retries).
- `final.{cu|cpp}` — copy of the passing attempt. Only exists if at least one attempt passed.
- `nsight_raw.csv` — raw ncu CSV output, kept for reproducibility.
- `nsight.xml` — parsed into the standard XML format (Section 5 of spec v5).
- `feedback.xml` — the `<Iteration_Feedback>` XML that was sent to the LLM for this round.
  Generated from the **previous round's** nsight.xml + baseline nsight.xml.
- `context.xml` — identical between cell_b and cell_c for the same benchmark.
  May be shared between CUDA and OMP variants if the algorithm analysis is language-agnostic.

## 3. Pipeline Flow Per Benchmark

```
For each benchmark:
│
├─ 1. Setup
│     Copy baseline .cu from HeCBench src/{name}-cuda/main.cu
│     Profile baseline with ncu → baseline/nsight_raw.csv
│     Parse → baseline/nsight.xml
│
├─ 2. Generate context (once, shared by Cell B and C)
│     Send baseline code + hardware_spec + empty template to analysis LLM
│     Save → cell_b/context.xml  (copy to cell_c/context.xml)
│
├─ 3. Run Cell A
│     Assemble prompt: system_prompt + cell_a_template + baseline code
│     Send to coding LLM → save attempt_1/main.cu
│     Compile → compile.log
│     If compile fail or validate fail:
│       retry with error (up to 3 attempts total)
│     If pass: copy to final.cu, profile with ncu
│     If 3 fails: mark FAIL
│
├─ 4. Run Cell B
│     Assemble prompt: system_prompt + cell_b_template + context + baseline code
│     Same correctness loop as Cell A
│
└─ 5. Run Cell C
      Round 1: same prompt as Cell B, same correctness loop
      For round 2..3:
        Generate feedback.xml from previous round's nsight.xml + baseline nsight.xml
        Assemble prompt: system_prompt + cell_c_round2_template + feedback.xml
        Same correctness loop
        If correctness FAIL: stop iterating, keep best previous result
```

## 4. ncu Profiling Command

```bash
# Profile a compiled binary and export CSV
ncu --set full \
    --csv \
    --log-file "${OUTPUT_DIR}/nsight_raw.csv" \
    --cache-control none \
    --clock-control none \
    "${BINARY_PATH}" "${BINARY_ARGS}"
```

Notes:
- `--set full` collects all metric sections (throughput, occupancy, memory, compute, stalls).
- `--cache-control none --clock-control none` avoids ncu locking clocks, giving results
  closer to real-world performance. Remove if you want deterministic profiling.
- If a benchmark launches multiple kernels, use `--kernel-name {name}` to target
  the specific kernel under test.
- Use `profile_to_xml.py` to convert the CSV to `<Iteration_Feedback>` XML.

## 5. Prompt Design Rationale

**Why the system prompt says "You do NOT have access to a compiler":**
Prevents the LLM from generating responses like "Let me first test this..." or producing
bash commands instead of CUDA code. Makes clear that its sole job is to output .cu source.

**Why Cell C round 2+ does not repeat the context XML:**
The context was given in round 1 within the same session. The LLM's context window
still contains it. Repeating wastes tokens and could cause the LLM to over-anchor
on the static analysis instead of the actual profiling data.

**Why correctness retry uses raw error output:**
No human interpretation of the error. This ensures the retry prompt is deterministic
and reproducible. The LLM sees exactly what nvcc or the runtime printed.

**Why there's no "round N of 3" indicator in prompts:**
Telling the LLM which round it's on might affect behavior (e.g., being conservative
in round 1 "because it has more chances"). The LLM should optimize as hard as it can
every round, without gaming the iteration budget.
