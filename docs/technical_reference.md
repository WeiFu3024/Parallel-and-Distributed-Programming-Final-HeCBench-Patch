# Technical Reference: LLM-Driven GPU Kernel Optimization Experiment
## For Coding Agent — Complete Specification

---

## 1. Experiment Overview

### 1.1 Goal
Evaluate LLM capability in optimizing GPU kernels by comparing three escalating levels
of information provision: blind optimization, context-guided optimization, and
iterative profiling-guided optimization.

### 1.2 Two Variants

The experiment runs in two parallel variants with identical Cell A/B/C structure:

| Variant | Directory | Language | Compiler | Execution | Profiler | Profile output |
|---------|-----------|----------|----------|-----------|----------|---------------|
| **CUDA** | `experiment-cuda/` | `.cu` | `nvcc` | GPU | `ncu` | `nsight_raw.csv` |
| **OMP** | `experiment-omp/` | `.cpp` | `g++ -fopenmp` | CPU | `perf stat` | `perf_raw.txt` |

Cross-variant comparison (CUDA GPU vs CPU OpenMP on the same benchmark) is a secondary analysis goal.

### 1.3 Three Experimental Cells

| Cell | Name | Round 1 Input | Round 2+ | Tests |
|------|------|--------------|----------|-------|
| A | Pure Code, Single Round | baseline code only | — | LLM's blind optimization ability |
| B | Context, Single Round | baseline code + LLM-generated context | — | Value of static analysis context (B vs A) |
| C | Context, Iterative | baseline code + LLM-generated context (= Cell B) | Full Nsight of baseline + own kernel | Value of iterative profiling feedback (C vs B) |

**Invariant:** Cell C round 1 prompt is identical to Cell B prompt.

### 1.4 Key Design Decisions Made

1. **Context is LLM-generated, not oracle.** A separate analysis LLM (same model) generates
   the context through pure static reasoning. No profiling data in context. This simulates
   a realistic "think before coding" workflow.

2. **Baseline Nsight is NOT given to Cell A or B.** Only Cell C receives Nsight data,
   starting from round 2. This keeps A→B comparison clean (only context differs) and
   B→C comparison clean (only iterative profiling differs).

3. **Baseline code is always provided.** The task is "optimize this existing CUDA kernel",
   not "write CUDA from scratch". HeCBench provides the baseline CUDA code.

4. **No `Optimization_Priority` field in context.** Removed because it would be too
   directive — the coding LLM should decide optimization strategy itself based on
   the analytical facts provided.

5. **Correctness retries are separate from optimization iterations.** Up to 3 attempts
   per round to produce a compilable, numerically correct kernel. This does not consume
   optimization iterations.

6. **LLM has no shell/tool access.** All compilation, execution, and profiling is
   performed by the human pipeline. The LLM only outputs .cu source code.

7. **No acceleration libraries.** LLM must write raw CUDA kernels (no cuBLAS, cuFFT,
   cuDNN, Thrust). The project's Baseline 2 already covers library-accelerated versions.

### Field Source Table

| Field | Source | Nature |
|-------|--------|--------|
| Problem_Classification | Analysis LLM reads source code | Algorithm identification + inference |
| Bottleneck_Analysis | Analysis LLM computes theoretical values from code + HW spec | Theoretical estimate (may be wrong) |
| Memory_Access_Profile | Analysis LLM traces data access patterns | Static analysis inference |
| Parallelism_Structure | Analysis LLM analyzes loop/dependency structure | Static analysis inference |
| Hardware_Constraints | Copied from deviceQuery / hardware_spec.sh | Ground truth (objective fact) |
| Data_Shape | Analysis LLM extracts from source code | Code inspection |

## 5. Execution Rules

### 5.1 LLM Sandbox
- No shell, compiler, profiler, or runtime access.
- No internet access.
- No acceleration libraries (cuBLAS, cuFFT, cuDNN, Thrust).
- Cannot modify host-side code (validation, input generation, data types, problem sizes).
- Output: single self-contained .cu file only.

### 5.2 Correctness Rules
- Within each optimization round, the LLM has up to **3 attempts** to produce a kernel
  that compiles and passes numerical validation (relative error < 1e-5 for float32).
- On compile failure or validation failure: feed raw error output back to LLM.
- Correctness retry counter **resets** at each new optimization round (Cell C).
- If 3 attempts exhausted:
  - Cell A / B: benchmark marked **FAIL**.
  - Cell C: stop iterating. Final result = best passing kernel from previous rounds.
    If no previous round passed, benchmark is **FAIL**.

### 5.3 Cell C Iteration Rules
- Maximum optimization iterations: **3 rounds**.
- Round 1 prompt = Cell B prompt (identical).
- Round 2+ prompt = Iteration_Feedback XML only (context is in session history).
- All rounds conducted in the same session (LLM sees conversation history).
- Final result: **best kernel time** across all passing rounds.
- Per-round data is recorded for convergence analysis.

## 6. DFA State Machine

```
States:
  S0: Start (select benchmark)
  S1: Build prompt (cell-dependent)
  S2: Send to LLM
  S3: Correctness check (compile + validate)
  S4: Profile with ncu
  S5: Iteration decision
  S6: Record result
  R:  Retry check
  F:  Fail

Transitions:
  S0 → S1                           for each benchmark
  S1 → S2                           prompt assembled
  S2 → S3                           LLM returns .cu code
  S3 → S4          [pass]           compile OK + validation pass
  S3 → R           [fail]           compile error or validation error
  R  → S2          [retry ≤ 3]      feed raw error to LLM
  R  → F           [retry > 3]      mark FAIL, stop
  S4 → S5                           ncu profiling complete
  S5 → S6          [Cell A/B, or Cell C round ≥ 3]
  S5 → S2          [Cell C, round < 3]   feed Iteration_Feedback XML
  S6 → done                         record best result

Entry conditions at S1:
  Cell A: system_prompt + code
  Cell B: system_prompt + context + code
  Cell C: round 1 = Cell B; round 2+ = Iteration_Feedback XML

Re-entry at S2 from S5 (Cell C iteration):
  New session message with Iteration_Feedback XML
  Correctness retry counter resets

Re-entry at S2 from R (correctness retry):
  Feed raw error message
  Same round, same retry counter
```

```
            ├── context.xml             ├── context.xml

            │   └── attempt_{1,2,3}/    │   └── attempt_{1,2,3}/
            └── (best result)           └── (best result)
```

### File Naming Conventions
- `attempt_N/main.cu` — Nth LLM submission within a round (correctness retries)
- `final.cu` — copy of the passing attempt's .cu. Exists only if a passing attempt exists.
- `nsight_raw.csv` — raw ncu CSV. Kept for reproducibility.
- `nsight.xml` — parsed profile in standard XML format.
- `feedback.xml` — Iteration_Feedback XML sent to LLM for this round.
  Generated from previous round's nsight.xml + baseline nsight.xml.
- `context.xml` — identical between cell_b and cell_c for the same benchmark.
- `compile.log` — nvcc stdout + stderr.
- `validate.log` — runtime output + correctness check result.

## 8. Profiling

### 8.1 CUDA — ncu
```bash
ncu --set full \
    --csv \
    --log-file "${OUTPUT_DIR}/nsight_raw.csv" \
    "${BINARY}" "${ARGS}"
```

Generate Iteration_Feedback XML for Cell C:
```bash
python experiment-cuda/scripts/profile_to_xml.py feedback \
    --baseline results/{bench}/baseline/nsight_raw.csv \
    --yours    results/{bench}/cell_c/round_N/nsight_raw.csv \
    --round N \
    --output   results/{bench}/cell_c/round_{N+1}/feedback.xml

# List available metric names (run once per ncu version):
python experiment-cuda/scripts/profile_to_xml.py discover --input nsight_raw.csv
```

`profile_to_xml.py` maps ncu metric names via a `METRIC_MAP` dict. Metric names vary across ncu versions — run `discover` first.

### 8.2 OMP — perf stat
```bash
perf stat -e \
  task-clock,cycles,instructions,branches,branch-misses,\
  L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses,\
  context-switches,cpu-migrations \
  -o "${OUTPUT_DIR}/perf_raw.txt" \
  -- env OMP_NUM_THREADS=$(nproc) "${BINARY}" "${ARGS}"
```

Notes:
- Intel CPUs can add L2: `l2_rqsts.references,l2_rqsts.miss`. AMD: check `perf list | grep l2`.
- If counter limit exceeded, perf multiplexes. Split into two runs for precision.

Generate Iteration_Feedback XML for Cell C:
```bash
python experiment-omp/scripts/perf_to_xml.py feedback \
    --baseline results/{bench}/baseline/perf_raw.txt \
    --yours    results/{bench}/cell_c/round_N/perf_raw.txt \
    --round N \
    --threads $(nproc) \
    --peak-bw <GB/s from hardware_spec> \
    --output   results/{bench}/cell_c/round_{N+1}/feedback.xml

# List counters found in a file:
python experiment-omp/scripts/perf_to_xml.py discover --input perf_raw.txt
```

   Nsight data from Cell C profiling.

## 10. Scripts Reference

Scripts exist independently in each variant directory. The two variants differ in compiler, hardware_spec output, and profiling tool.

| Script | CUDA | OMP | Purpose |
|--------|------|-----|---------|
| `hardware_spec.sh` | GPU info (nvidia-smi, deviceQuery) | CPU info (lscpu, numactl, perf) | Hardware spec for context XML |
| `init_experiment.sh` | copies `main.cu` from `-cuda/` | copies `main.cpp` from `-omp/` | Create dir tree + baseline |
| `compile.sh` | `nvcc`, arch `sm_XX` | `g++ -fopenmp`, no arch | Compile LLM attempt → `main` |
| `validate.sh` | identical | identical | Run + check correctness |
| `profile_to_xml.py` | parses ncu CSV → XML | **not present** | ncu CSV → Iteration_Feedback XML |
| `perf_to_xml.py` | **not present** | parses perf stat txt → XML | perf stat → Iteration_Feedback XML |

### compile.sh — CUDA (`experiment-cuda/scripts/compile.sh`)

```bash
bash experiment-cuda/scripts/compile.sh <hecbench_path> <benchmark> <cell> <round> <attempt> [sm_arch]

# Example:
bash experiment-cuda/scripts/compile.sh ~/HeCBench accuracy cell_a 1 1
bash experiment-cuda/scripts/compile.sh ~/HeCBench fft cell_c 2 1 sm_89
```

- Compiler: `nvcc`. Arch flag format: `sm_86`.
- Auto-detects SM arch from `nvidia-smi` if not specified.
- Writes `compile.log`; final line `COMPILE: SUCCESS` or `COMPILE: FAIL (nvcc exit N)`.

| Benchmark | Copied deps | Extra nvcc flags |
|-----------|-------------|-----------------|
| `accuracy` | `reference.h` | — |
| `aes` | `aes.h`, `kernels.cu`, `reference.cu`, `utils.cu` | `-I{hecbench}/src/include` |
| `fft` | `fft1D_512.h`, `ifft1D_512.h`, `reference.h` | — |

### compile.sh — OMP (`experiment-omp/scripts/compile.sh`)

```bash
bash experiment-omp/scripts/compile.sh <hecbench_path> <benchmark> <cell> <round> <attempt>

# Example:
bash experiment-omp/scripts/compile.sh ~/HeCBench accuracy cell_a 1 1
```

- Compiler: `g++` with `-fopenmp`. No arch flag — CPU target, optimized with `-O3`.
- Flags: `-std=c++17 -O3 -fopenmp`.
- Source file: `main.cpp` (not `.cu`).

| Benchmark | Copied deps | Include path |
|-----------|-------------|-------------|
| `accuracy` | (none) | `-I{hecbench}/src/accuracy-cuda` (shared `reference.h`) |
| `aes` | `aes.h`, `kernels.cpp`, `reference.cpp`, `utils.cpp` | `-I{hecbench}/src/include` |
| `fft` | (none) | `-I{hecbench}/src/fft-cuda` (shared `reference.h`) |

Note: `reference.cpp` is `#include`d inline by `aes-omp/main.cpp` and must be present in the attempt dir.

### validate.sh (identical for both variants)

```bash
bash experiment-{cuda|omp}/scripts/validate.sh <hecbench_path> <benchmark> <cell> <round> <attempt>
```

- Requires compiled `main` binary. Timeout: 120s per run.
- Writes `validate.log`; final line `VALIDATION: PASS` or `VALIDATION: FAIL`.

| Benchmark | Run arguments | Pass condition |
|-----------|---------------|----------------|
| `accuracy` | `8192 10000 10 100` | No `FAIL` lines; at least one `PASS` line |
| `aes` | `100 0 <bmp>` then `100 1 <bmp>` | No `Fail`; at least 2 `Pass` lines |
| `fft` | `3 100` | `FFT PASS` and `iFFT PASS` present; no ` FAIL` |

**aes pre-requisite:** `URNG_Input.bmp` is a DVC artifact. Pull before running:
```bash
cd ~/HeCBench && dvc pull
```
